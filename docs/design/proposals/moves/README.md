- 日期：2026-11-23
- 所属层次：结构层（动作标签怎么组织、怎么跳转）+ 框架层（动作详情页放什么）
- 状态：**提案，待负责人选择**。选定后写决策记录，再改 `docs/design/app-structure.md`。
- 打开方式：用浏览器打开本目录的 `index.html`，四个手机框并排；截图在 `shots/`。
- 调研：`docs/design/research/2026-11-23-moves-library.md`
- 视觉：沿用方向 A（决策 0009）。`tokens.css` 复制自 `apps/app/src/styles/tokens.css`；`shared.css`、`skin.css` 原样复制自 `docs/design/mockups/`；本提案新增的组件都在 `moves.css`。

## 两个方案一句话

| | 方案一 · 分类目录 | 方案二 · 部位与风格筛选 |
|---|---|---|
| 首页 | 顶部搜索 + 五个分类的锚点芯片；下面是按分类分组的动作列表 | 两排筛选（部位、风格）+ 带姿势插图的两列卡片 |
| 到达半握 | 动作 → 点"半握"（1 次点击） | 动作 → 点"半握"卡片（1 次点击；默认筛选不对时再加 1–2 次） |
| 详情页重心 | 文字为主，信息密；角色标签标在每一行 | 图示为主；先看"用到哪里"，结构按角色分组 |
| 负责人的"风格"想法 | 不出现（风格可以日后作为动作属性显示） | 作为第二排筛选条件 |

## 方案一 · 分类目录

**思路**：沿用已定的五个分类（`content/sports.json`）。原先设想的"分类列表 → 动作列表 → 详情"三层，合并成一屏分组目录：分类就是小节标题，顶部芯片点一下跳到对应小节。第一版只有约 15 个动作，一屏多一点就能看完，没必要多一层。

**首页**（`option-1/home.html`）
- 常驻搜索框，提示可以搜别名和英文（如 crimp）。
- 五个分类芯片，可横向滑动，点击跳到该小节。
- 每行：中文名、英文名、涉及部位（如"手指 · 腕"）。部位只是说明，不是风险提示。
- 动作多的分类只显示前几个，末尾"查看全部"。

**详情**（`option-1/detail.html`）
- 分类、名称、英文名、别名、一句话说明、内容状态徽标（与损伤页一致）。
- 右上角 3D 缩略图 + 一个明确的"在 3D 中查看"按钮。
- "发力结构 | 易伤部位"两个分页。发力结构每行右侧是角色标签：主动肌（实心）、协同肌（描边）、稳定肌（灰描边）、受力结构（虚线，对应"受力的非收缩结构"，标签里写全称太长，所以缩写）；列表下方有"这四种角色分别是什么意思？"的说明入口。
- 易伤部位每条：结构 → 对应损伤（可点）+ 一句定性说明。顶部固定一句"只做一般说明，不代表个人情况"。没有分数、没有红黄绿。
- 底部"相近的动作"（如开手握、全握），方便对比。

**优点**
- 与已有的数据结构、`app-structure.md` 完全一致，**不用改 schema**。
- 名称就是攀岩者的说法，扫一眼就找到；知道名字的人直接搜。
- 实现简单：列表、锚点、搜索都是普通组件；不需要为每个动作画插图。
- 内容少时不显得空，内容多了也能撑住（每个分类折叠显示）。

**缺点**
- 观感偏"目录"，缺少视觉记忆点；不知道动作叫什么的新手需要靠搜索或先去"身体"标签。
- "从部位出发"的需求不在这里解决（由身体标签承担）。

**更适合的用户任务**：任务 2"想知道某个动作在用哪些结构、哪里容易伤"——用户一般已知道动作名（"我最近半握用得多"）。教练备课查找某个动作也很快。

## 方案二 · 部位与风格筛选

**思路**：以"部位"为第一入口，因为我们的主要用户是"手指、肩担心受伤"的人；再用"风格"（静态 / 动态 / 跳跃 Dyno）作为第二个筛选条件，这是负责人最初的想法。结果用卡片展示，每张卡片有一张自绘的姿势示意图。

**为什么风格是筛选条件而不是第一层**：负责人原话是"攀岩 → 风格（静态、动态、Dyno）→ 动作库"。问题在于风格只描述身体怎么动，不描述手怎么抓——半握在静态和动态动作里都用；坠落与落地、专项训练也归不进这三类。如果硬做第一层，就会出现"其他"兜底分组。所以这里把风格降为筛选条件；抓法类动作在任何风格下都会出现。**这一点和负责人的原始想法不同，请确认。**

**首页**（`option-2/home.html`）
- 部位：全部 / 手指 / 腕与前臂 / 肘 / 肩（第一版没有下肢内容，所以不放）。
- 风格：全部 / 静态 / 动态 / 跳跃 Dyno。
- 结果条显示当前筛选与数量，并提供"列表视图"（准则 6.9：图之外有列表等价入口）。
- 卡片：示意图、分类、名称、英文名、"用到：手指 · 前臂"。

**详情**（`option-2/detail.html`）
- 顶部大示意图，标出关键关节（角度为占位）。
- 名称、别名、说明、状态徽标；一个醒目的实心按钮"在 3D 中查看用到的结构"。
- "用到哪里"小卡：简笔人形上高亮涉及的部位，一句话概括。
- "发力结构 | 易伤部位"两个分页。发力结构**按角色分组**，每组有一句角色解释，不需要另找说明。
- 易伤部位做成卡片：结构 → 损伤名 → 定性说明 →"看这种损伤是怎么回事"。
- 底部"同一部位的其他动作"卡片。

**优点**
- 更直观，有记忆点；示意图让不熟悉术语的人（家长、新手）也能认出动作。
- 按角色分组 + 组内解释，对非专业用户更友好。
- 承接了负责人的风格想法；"部位"入口贴近主要用户的担忧。

**缺点**
- 第一版约 15 个动作，两排筛选一组合，结果常常只剩两三个，筛选显得多余；顶部筛选区也占掉约四分之一屏。
- 需要改数据：动作要加"风格"字段（schema 变更，需写决策记录）；部位可以从结构的 `region` 字段推出来，但一个动作跨多个部位时，"出现在哪个部位下"需要规则。
- 每个动作要画一张示意图（约 15 张），图要准确到关节角度，需要和文字一样对照来源审核，否则示意图本身就可能传达错误信息。
- 跟"身体"标签的"从部位出发"有重复。

**更适合的用户任务**：任务 3"想理解自己的身体"、浏览式学习；对家长和新手更友好。

## 实现代价（粗估，供比较）

| | 方案一 | 方案二 |
|---|---|---|
| 数据结构 | 不变 | 动作加 `style` 字段；定义部位归属规则；改 schema 与校验 |
| 素材 | 无新增（3D 缩略图可用现有渲染） | 每个动作一张自绘示意图（约 15 张），需审核准确性 |
| 界面组件 | 搜索、分组列表、锚点芯片 | 搜索、双排筛选、卡片网格、示意图组件、"用到哪里"人形图 |
| 测试 | 现有完整性测试即可 | 还要测"每个动作有风格、有示意图" |
| 相对工作量 | 1 | 约 2–2.5 |

## 我的推荐

**选方案一（分类目录），并从方案二借两样东西：**

1. 详情页"发力结构"**按角色分组并附一句解释**（方案二的做法）——这对非专业用户更友好，而且不需要改数据。
2. 详情页顶部"用到哪里"的小人形图可以作为后续增强，先不做。

理由：
- 第一版内容量小，分组目录一屏可见，筛选的收益抵不过它的空间和改数据的代价。
- 不改 schema、不新增素材，能更快进入 0.2 骨架阶段，先让真实用户试用。
- "从部位出发"已经有身体标签承担；动作标签负责"从动作名出发"，分工清楚。
- 风格可以先作为详情页上的一个说明标签显示（如"动态"），等动作多了再考虑升级为筛选。

## 需要负责人回答的问题

1. **选方案一还是方案二**，或者"方案一 + 角色分组"这个折中。
2. **风格（静态 / 动态 / Dyno）放在哪**：同意把它从"第一层"降为属性或筛选条件吗？理由见方案二开头。
3. 详情页**角色标签的写法**：方案一的"受力结构"是"受力的非收缩结构"的缩写，能接受吗？还是宁可写全称、多占一行？
4. **示意图**：愿意为每个动作投入一张自绘示意图吗？它需要和文字一样经过来源核对。如果暂时不做，详情页就用 3D 缩略图。
5. 动作首页底部是否需要那条免责声明？目前每页都有（与已有样稿一致），列表页可以考虑只在详情页显示，以节省空间。
