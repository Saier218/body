# 0003 小程序内的 3D 技术路线

- 状态：**待真机验证**（浏览器内的契约测试已通过；微信开发者工具与真机尚未运行）
- 日期：2026-11-15（当日对照微信官方文档核实）

## 结论

用 three.js（MIT）直接画在小程序原生的 WebGL2 画布上。3D 逻辑写成一个与平台无关的核心模块，小程序只是一层薄外壳。

```
packages/viewer-core   3D 核心：渲染、旋转缩放、点选、分区聚焦、图层开关。不含任何 wx.* 或浏览器专有调用
apps/miniprogram       小程序外壳：取画布、读模型文件、把触摸事件转给核心、显示文字
tools/modeling         模型流水线：从 BodyParts3D 取分区、生成滑车、打包压缩
tools/contract-test    契约测试：在去掉浏览器专有能力的环境里运行核心
```

## 核实到的平台事实（来源：微信官方文档，2026-11-15 读取）

| 事实 | 对设计的影响 |
|---|---|
| `canvas` 组件支持 `webgl`（基础库 2.7.0 起）；`getContext` 支持 `webgl2`（2.24.0 起） | three.js 0.170 只支持 WebGL2，因此最低基础库为 2.24.0 |
| 主包与每个分包不超过 2 MB，全部分包合计不超过 30 MB | 当前核心 0.48 MB 加模型 0.89 MB，合计约 1.4 MB，放在主包内可行但余量小；内容增多后模型要移到分包或 CDN |
| 只有白名单后缀的文件会被上传，`.glb` 不在其中，`.br` 和 `.json` 在 | 模型以 brotli 压缩后的 `.glb.br` 入包 |
| `FileSystemManager.readCompressedFile` 可读代码包内的 brotli 文件（2.21.1 起） | 用它在运行时解压模型 |
| 开发者工具默认关闭 GPU 硬件加速；WebGL 不支持"真机调试"，只能"真机预览" | 写进操作说明 |
| `web-view` 会铺满整页并覆盖其他组件，且需配置业务域名 | 否决 web-view 方案，见下 |
| 开发者工具内置 TypeScript 编译插件（`useCompilerPlugins`） | 页面直接写 TypeScript，无需额外构建 |

## 被否决的选项

- **web-view 内嵌网页**：技术上最省事，但整页被网页占满、需要已备案的业务域名、与原生界面通信受限，体验和审核都更差。
- **微信官方 3D 框架（xr-frame）**：只能在微信内运行，日后做 App 要重写，违反准则 6.4。
- **官方的 three.js 适配库 threejs-miniprogram**：未采用。我们让核心只依赖画布的 5 个成员（宽、高、取上下文、请求帧、取消帧），并自己写了一个只支持我们模型格式子集的 GLB 读取器，从而不需要任何适配库。
- **three.js 自带的 glTF 加载器**：依赖 TextDecoder、Blob、fetch，小程序运行环境不保证提供。

## 若验证失败的退路

- WebGL2 在部分机型不可用：改用仍支持 WebGL1 的 three.js 旧版本（0.162 及以下），核心代码基本不变。
- 帧率不足：按分区加载、降低模型面数、合并同类网格以减少绘制次数（目前 103 个结构即 103 次绘制）。
- 压缩文件读取不可用：改为从 CDN 下载模型。
