# 架构总览

一句话：**内容是数据，3D 是一个可替换的显示部件，平台只是外壳。** 这三者分开，任何一个变化都不牵动另外两个。

## 分层

```
┌──────────────────────────────────────────────────────────────┐
│ 原生外壳              ios/  android/  （Capacitor 生成）      │
│   只负责把下面的界面装进一个 App，不写业务逻辑                │
├──────────────────────────────────────────────────────────────┤
│ 界面（网页技术）      apps/app                                │
│   页面、文字、触摸事件、读模型文件、本地存储                  │
├──────────────────────────────────────────────────────────────┤
│ 3D 核心（平台无关）   packages/viewer-core                    │
│   渲染、相机、点选、分区聚焦、图层开关                        │
├──────────────────────────────────────────────────────────────┤
│ 内容（纯数据）        目录文件、动作、损伤、来源（待建）      │
│   每个结构一个稳定编号，模型与内容靠这个编号对应              │
├──────────────────────────────────────────────────────────────┤
│ 流水线（离线运行）    tools/modeling                          │
│   原始模型 → 取分区 → 补建结构 → 打包 → 目录文件              │
└──────────────────────────────────────────────────────────────┘
```

同一份 `apps/app` 有三种运行方式：在浏览器里（开发和自动测试用）、在 iOS 外壳里、在 Android 外壳里。
`apps/miniprogram` 是冻结的小程序外壳，不再维护（决策 0004）。

## 数据怎么流动

1. **离线**：流水线读取 BodyParts3D 原始模型和文献参数，产出两个文件：模型（几何形状）和目录（每个结构的编号、中英文名、类别、所属分区）。
2. **运行时**：界面读取这两个文件交给 3D 核心。核心只认编号，不认识任何医学内容。
3. **交互**：用户点击 → 界面把触摸坐标交给核心 → 核心算出点中了哪个编号 → 界面用编号去内容数据里查名称、相关动作和损伤并显示。

## 贯穿全局的约定

| 约定 | 为什么 |
|---|---|
| 结构编号是唯一的连接点 | 模型可以重做、内容可以重写，只要编号不变就互不影响 |
| 核心只依赖画布的 5 个成员 | 换平台时只需重写薄薄的一层界面适配（这次从小程序换到 App 就是这样做的） |
| 医学内容不写在代码里 | 可以逐条核对来源、单独下线有误条目 |
| 每条数据带来源与状态 | 合规和可信度的基础（准则第 5 节） |
| 界面文字全部走文字表 | 中英双语从第一天成立 |
| 用户数据读写集中在一个模块 | 本地存储日后可换成云同步（决策 0002） |

## 质量关口

一条命令全跑：`npm run check`

- 类型检查：核心单独用"不含浏览器类型"的配置检查，写了浏览器专有代码会直接报错
- 端到端测试（`npm run test:app`）：在模拟手机触屏的浏览器里打开构建好的 App，真实地点击、切换语言、开关图层、旋转屏幕
- 契约测试（`npm run test:contract`）：在去掉浏览器专有能力的环境里运行核心
- 待建：内容数据的完整性校验（每条损伤有来源、每个编号在模型中存在）
